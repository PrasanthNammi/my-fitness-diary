### Previous and new flow

Previously `startGoogle` generated independent random application state and PKCE verifier, stored the entire pending context in a five-minute HttpOnly cookie, and included application state in redirect_to. Callback compared returned state and browser context before exchanging the code. Cookie clearing and Supabase one-time code redemption provided replay resistance, but there was no shared server-side consumed-transaction ledger. This created the allowlist query dependency investigated above.

**Supabase provider OAuth state** is separate: Supabase handles its own Google provider transaction/state and Google callback validation. MFD does not construct or override that provider state. The old **MFD application state** was a separate browser transaction value; it is now an opaque 256-bit transaction ID held only in an HttpOnly cookie and the private server record, never appended to redirect_to. Supabase still handles Google nonce/provider token verification. The independent Worker uses Supabase's pinned Auth endpoints directly, rather than adding a new supabase-js signInWithOAuth client or custom OAuth issuer.

New flow:

1. GET `/login` retains the password form and issues a stable, random `__Host-mfd-integration-browser` cookie if absent/invalid, plus the existing per-form CSRF token/cookie. Cookies are Secure, HttpOnly, SameSite=Lax, Path=/, no Domain. Browser binding lasts 30 minutes; a transaction/flow cookie lasts five minutes.
2. POST `/auth/google` retains exact Origin, cross-site, form/size/duplicate-field, CSRF, relative-continuation and shared-quota checks. It requires the browser secret and a working private transaction store. Random transaction ID and verifier are 32 bytes each, hex encoded. S256 challenge is still mandatory.
3. A private RPC to the **same existing** `AbuseCoordinator` inserts the context atomically under the SHA-256 browser-secret fingerprint. The row holds transaction ID, verifier, validated pending authorization continuation, existing verified owner/session fingerprint if present, and expiry. Neither browser cookie contains that record. No raw access/refresh token, password, email or Google credential is persisted.
4. The exact redirect_to is now always:

   `https://mfd-connect-staging.shanustylish777.workers.dev/auth/google/callback`

   No application state, owner, authorization_id, verifier or token is appended. The provider's returned one-time code/error query remains necessary protocol data; do not claim callbacks are completely query-free or that platform access logs cannot capture codes.
5. Callback requires both opaque transaction and browser cookies. Private RPC matches both values and atomically removes the row **before** parsing/exchange. Wrong browser/ID cannot consume another row. Expired/missing/consumed rows fail closed. Errors/cancellation consume the matching transaction too; no retry resurrection.
6. Callback permits only singleton code/error/error_code/error_description fields, rejects the former application `state` query and all unexpected/duplicate fields, and validates the code bounds. The saved verifier alone is used for pinned `/token?grant_type=pkce`; a code from another browser/transaction cannot pass genuine provider PKCE verification.
7. Existing browser account/token fingerprint must still match initiation. The exchange user UUID must match the independently upstream-verified token subject, issuer, first-party audience/role, live session-shaped claims, expiry/nbf and absence of MCP client claim. Native consent still enforces its authorization-user match; fixed RPC still derives owner and checks live client/session/section consent. Browser cookies cannot authenticate `/mcp`.

### Concurrency, persistence and fail-closed boundaries

One pending transaction per browser fingerprint is enforced by the SQLite primary key inside `transactionSync`. Concurrent starts for an already-pending browser fail without replacing the first flow; concurrent callbacks produce exactly one winner. Two first visits racing before a browser cookie exists can generate separate browser identities; the browser's final cookie determines its usable flow, and a mismatched verifier/binding fails closed. Availability is not guaranteed for racing tabs; restart login after expiry or an approved logout, never weaken binding.

Unknown/expired cookies, storage outage/capacity, failed creation, alarm-scheduling failure, timeout or missing RPC fail closed. Colocated RPCs have a two-second deadline and no in-memory fallback. A late timed-out operation may conservatively create/consume a transaction without granting login; wait for expiry/restart rather than replaying it. Split-host auth-worker has no distributed transaction binding and therefore fails closed for Google initiation; password login remains. The selected colocated architecture is the supported local path.

The unchanged rate budgets still apply **before** transaction/Auth work. A new `google_transactions` table is bounded to **128 rows**, in addition to the original four counter rows. Expiry is enforced on every take; expired rows are removed on create and by the DO alarm. A successful create schedules cleanup five minutes later; each alarm deletes expired rows and reschedules if any remain. Cleanup delivery/delay is a provider behavior, not a hard storage-erasure deadline. Expired records can remain while an object is idle or an alarm is delayed but cannot authenticate. No new public storage endpoint, namespace, class, binding, managed privilege or external service was introduced. Existing SQL DO class initialization creates the table locally; no hosted migration/deployment occurred.

**Storage privacy/cost change:** earlier “four rows/no account IDs persisted” statements describe counters only and are superseded for this design. Pending records include a verified Supabase owner UUID when initiation had a session, its token fingerprint, continuation and PKCE verifier. Treat the private object/storage and diagnostics as sensitive; no request/context dumps or SQL-row logging. Cloudflare platform storage/PITR retention may outlive logical deletion and needs review before deployment. This is temporary server-side authentication material, not diary data or a secret Supabase key. Keep per-request authorization independent of this record.

Additional transaction inserts/deletes, primary-key index accounting, RPCs and alarm/storage metadata add usage. The old two-counter-writes/admission estimate is **not** a total quota bound anymore. No paid service/upgrade/dependency was added; controlled staging within existing allowances remains the objective, but worst-case sustained auth traffic may exhaust Free SQLite writes. Preserve fail-closed behavior; revise quota/cost planning and measure metering before a broader deployment. No zero-cost or availability guarantee and no automatic limiter increase.

Fixed callback security uses browser possession plus single-use server record and PKCE rather than an application state returned in the URL. An unsolicited top-level callback can consume a matching pending transaction and cause login failure; it cannot authenticate an injected account without the matching verifier and verified identity. Malformed/provider-error callbacks intentionally burn the record. This is a fail-closed availability tradeoff, not proof of a globally uninterruptible login process.
